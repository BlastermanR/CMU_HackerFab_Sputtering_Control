================================================================================
                        SputterOS - SYSTEM ARCHITECTURE SPECIFICATION
================================================================================
TARGET HARDWARE: Raspberry Pi Pico 2 (RP2350)
TARGET CLOCK:    125 MHz (Downclocked for stability/thermal management)
CORE MAPPING:    Core 0 -> External Communications & Command Parsing
                 Core 1 -> Hardware Control, State Machine & Interlocks
================================================================================

1. INTER-CORE COMMUNICATION (IPC) MANAGER
--------------------------------------------------------------------------------
Purpose: 
Provides a thread-safe, non-blocking bridge between Core 0 (which handles unpredictable serial commands from a PC/HMI) and Core 1 (which requires strict, uninterrupted timing for sputtering hardware control).

Architecture:
* Core Interface: Utilizes the RP2350 hardware FIFOs (via `pico_multicore` library).
* Data Structure: Passes fixed-size command packets (Structs/Enums) rather than raw strings. For example: `[Command ID (8-bit)] | [Target Device (8-bit)] | [Value (32-bit Float/Int)]`.
* Concurrency Protection: Uses hardware spinlocks (`hardware_sync`) for any shared memory (e.g., shared state variables) that bypass the FIFO to ensure no race conditions occur when Core 0 tries to read the current vacuum pressure while Core 1 is updating it.
* Execution Flow: 
  - Core 0 parses incoming serial -> creates a Command Struct -> pushes to FIFO.
  - Core 1 polls FIFO at the start of its tick -> pops Command Struct -> executes hardware change.

2. SAFETY INTERLOCK & WATCHDOG MANAGER [CRITICAL]
--------------------------------------------------------------------------------
Purpose: 
Acts as the ultimate fail-safe. Sputtering involves plasma, high voltage, and deep vacuum. If the software crashes, serial connection drops, or a gauge faults, the hardware must physically default to a safe state.

Architecture:
* Watchdog Timer (WDT): Configured via `hardware_watchdog` with a tight timeout (e.g., 500ms). Core 1 must "kick" the watchdog every loop cycle. If Core 1 hangs, the WDT triggers a hard silicon reset.
* Hardware Defaulting: On boot (and on WDT reset), all GPIO pins connected to high-voltage supplies, RF generators, and mass flow controllers must initialize to OFF/0V. Valves must initialize to their safe state (e.g., Chamber Vent Valve = CLOSED, Roughing Valve = CLOSED).
* Soft Interlocks: Continuously polls critical constraints before allowing state transitions. 
  - Example: Cannot transition to 'IGNITE_PLASMA' unless 'PRESSURE < 5e-3 Torr' AND 'ARGON_FLOW > 10 sccm' AND 'WATER_COOLING_FLOW == TRUE'.
* Physical Isolation Layer: Requires external hardware integration (Optocouplers) to protect the Pico 2 from EMI/RF noise generated by the plasma.

3. NON-BLOCKING TASK SCHEDULER / STATE MACHINE
--------------------------------------------------------------------------------
Purpose: 
Replaces all `sleep_ms()` calls with a deterministic execution engine. Allows Core 1 to handle slow events (waiting for pump-down) and fast events (PID gas flow control) simultaneously without halting.

Architecture:
* Timing Engine: Uses the Pico's 64-bit microsecond timer (`time_us_64()`). Tasks are evaluated based on delta time: `if (current_time - last_run_time >= interval) { run_task(); }`
* Task Registry: An array or vector of function pointers/functors with assigned intervals (e.g., ReadGauges: 50ms, UpdatePID: 10ms, CheckInterlocks: 1ms).
* The Sputtering State Machine: A strongly-typed enum tracking the physical phase of the machine:
  1. SYSTEM_IDLE
  2. ROUGH_PUMPING (Atmosphere down to crossover pressure)
  3. HIGH_VAC_PUMPING (Crossover down to base pressure)
  4. GAS_STABILIZATION (Flowing Argon, waiting for pressure to equalize)
  5. IGNITE_PLASMA (Applying voltage)
  6. DEPOSITION_HOLD (Maintaining stable plasma for X seconds)
  7. VENTING (Returning chamber to atmosphere safely)

4. ERROR LOGGER & DIAGNOSTICS
--------------------------------------------------------------------------------
Purpose: 
Maintains a post-mortem record of system operations. When a deposition fails or an interlock trips, this provides the specific telemetry that caused the abort.

Architecture:
* Ring Buffer (RAM): A circular buffer of the last N system events and sensor readings. Operates purely in SRAM (fast, no Flash wear-and-tear).
* Event Struct: `[Timestamp (ms)] | [Event Level (INFO/WARN/CRITICAL)] | [Component Code] | [Value]`
* Serial Stream Hook: Diagnostics are streamed asynchronously out of Core 0 when requested by the external controller.
* Crash Dump (Optional): If the Interlock Manager detects an unrecoverable fault, it freezes the state machine and dumps the contents of the Ring Buffer over the serial port to the host PC before allowing a system halt or reset.
